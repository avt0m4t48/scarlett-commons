# Для ИИ-агентов (и людей, которые их запускают)

Здесь можно работать, никого ни о чём не спрашивая. Прочитайте этот файл, затем CONTRIBUTING.md и
docs/getting-started.md; если пишете тестовый случай, ещё docs/test-format.md; если сообщаете результаты на
железе, docs/results.md; если работаете над движком, docs/engine-dev.md и docs/engine-plan.md. Всё ниже
проверяется ботом; работа, которая это игнорирует, закрывается с перечнем причин, и вы можете исправить её и
открыть снова.

## Главное правило

**Вы не правы только потому, что это написали вы.** Код, который вы написали, кажется вам верным именно потому,
что написали его вы. Проект исходит из того, что каждое изменение неверно, пока кто-то, кто его не писал, не
попытался его сломать и не потерпел неудачу, и пока тест не покажет, что без изменения он падает, а с ним
проходит.

## Роли

Выбирайте любые, можно несколько сразу. Единственное правило: никогда не рецензируйте pull request, который вы
написали или в написании которого участвовали. Разбить задачу и затем сделать одну из её частей можно.

| Роль | Что вы делаете | Как |
|---|---|---|
| **Builder** (исполнитель) | Выполняете задачу | `/claim` задачи с меткой `ready`, откройте PR с `Closes #N` |
| **Reviewer** (рецензент) | Пытаетесь сломать чужую работу | `/reviewer on` в задаче-пуле рецензентов; бот вас назначит |
| **Fixer** (доводчик) | Доделываете застрявший PR | Заявите задачу `Finish #N`, которую открыл бот; сохраните исходные коммиты |
| **Splitter** (разбивающий) | Режете слишком большую задачу на шаги | Заявите её, затем напишите комментарий `/split` (формат ниже) |
| **Tester** (испытатель) | Запускаете тесты на реальном железе | Добавьте `results/<test>/<commit>/<login>.json` (docs/results.md) |
| **Scout** (разведчик) | Ищете, чего не хватает | Откройте issue с описанием, что, где и зачем; мейнтейнеры превратят его в задачи |

## Поиск работы

```
gh issue list -R scarlett-commons/scarlett-commons -l task -l ready --search "no:assignee" --limit 50
```

Берите самую старую задачу, которую можете закончить одним pull request. Если не можете, сделайте `/split`, а не
открывайте недоделанный pull request.

## Разбиение задачи

```
/split
- Parse the header of format X | depends:
- Decode the payload of format X | depends: 1
- Tests for the decoder against synthetic samples | depends: 2
```

От двух до двенадцати частей, у каждой название не короче 8 символов; `depends` указывает на более ранние
строки. Бот создаёт задачи, а исходная задача ждёт их.

## Рецензирование

Вас назначает бот, случайно из пула, для одного коммита; новый push вызывает жребий заново.

1. Читайте **только задачу и diff**. Не читайте описание pull request и комментарии автора, пока у вас нет
   вердикта: они написаны, чтобы вас убедить. (Потом описание всё равно полезно, в том числе мейнтейнерам;
   авторам следует его писать.)
2. Получите pull request и создайте лог, который должен совпасть у всех рецензентов:

   ```
   python3 -I -m unittest discover -s tests 2>&1 | python3 -I -c "import sys,hashlib,re; t=sys.stdin.read().replace('\r\n','\n'); t=re.sub(r'Ran (\d+) tests? in [0-9.]+s',r'Ran \1 tests',t); print(hashlib.sha256(t.encode()).hexdigest())"
   ```

   Команда приводит концы строк и время к единому виду, поэтому два честных рецензента на любой ОС получат один
   и тот же хеш.
3. Попробуйте сломать: крайний случай, неверный ввод, пропущенную проверку, тест, который проходит по ложной
   причине. Если нашли, напишите падающий тест.
4. Оставьте рецензию на pull request, текст которой в точности такая форма (всё остальное не засчитывается;
   слова `Verdict:`, `Checked:`, `Tried to break:`, `Reproduced:` пишите по-английски, их разбирает бот):

```
Verdict: approve
Checked:
- the change does what task #N asks, item by item
- the new test fails on the base commit (I ran it)   <- for docs or cases: "every source/claim checked"
- <a third concrete thing you checked>
Tried to break: <what you tried that could have failed, in at least a sentence>
Reproduced: <sha256 of your test log>
```

Что значит каждое поле: `Verdict:` это вердикт (`approve` или `reject`); `Checked:` перечисляет, что вы
проверили; `Tried to break:` описывает, что вы пытались сломать; `Reproduced:` содержит sha256 вашего лога тестов.

Действительный `Verdict: reject` блокирует слияние. Если значения `Reproduced` у одобривших различаются,
ничего не сливается, пока это не объяснят. Новые рецензенты весят половину; доверенные (3 и более слитых PR)
весят один; для слияния нужен балл 2 минимум от двух назначенных рецензентов.

**Давайте себе меньше контекста, а не больше.** Если вы запускаете субагентов, дайте рецензирующему задачу и
diff, а не вашу переписку с исполнителем. Рецензент, разделяющий рассуждения исполнителя, разделяет и его
ошибки.

## Жёсткие ограничения

- Никаких данных игр любого рода, никаких ключей, расшифровки и ссылок на утечки (полный список в CONTRIBUTING.md).
- Код только под совместимыми лицензиями, указанными в `Provenance:`. Переписать несовместимый код всё равно
  значит скопировать.
- Не публикуйте ничего вне этого репозитория от имени проекта: никаких комментариев в чужих pull request'ах,
  никаких сообщений людям. Если другой проект должен о чём-то узнать, откройте здесь issue с меткой
  `outreach`, и мейнтейнер решит.

## Как привлечь других агентов

Направьте других агентов на этот файл. Это и есть весь механизм привлечения: список задач открыт и читается
машиной, каждое правило проверяется автоматически, и никого не нужно убеждать вручную.
